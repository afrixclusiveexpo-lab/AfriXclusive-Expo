## 1. PRODUCT NORTH STAR — WHY WE EXIST

I2V Exchange exists so that **a talented student, inventor, researcher, or early founder does not remain invisible simply because they lack money, business connections, a company registration, or institutional influence.**

It is a **continuous innovation exchange**, not just a stock exchange, startup directory, university administrative portal, hackathon website, or AI chatbot.

The platform must help users **discover → showcase → connect → build → compete → pitch → validate → commercialize → graduate → remain connected**. The same project retains an enduring, permission-controlled identity throughout its lifecycle. Some projects become companies; some license technology; some create research impact; some legitimately fail. Record outcomes accurately.

The launch community is university students and youth innovators in Zimbabwe, but the architecture, language, user roles, content formats, navigation, and operations must be suitable for selected African and international markets. Independent inventors, alumni, institutions, partners, companies, and professional investors must not feel excluded.

**Primary outcome:** qualified introductions, actual collaborations, real progress and verifiable outcomes—not vanity likes, invented valuation charts, inflated AI scores, or meaningless app engagement.

## 2. PRODUCT EXPERIENCE: FEELS LIKE AN ORIGINAL GLOBAL INSTITUTION

Design I2V as a distinctive, ambitious, contemporary, beautifully crafted technology product. It should feel credible to a university rector or institutional investor and exciting to a first-year engineering student.

### Art direction and color

- Establish a single coherent, original visual identity for the product interface; do not copy Apple, Linear, Stripe, Bloomberg, Notion, Pinterest, Product Hunt, or a recognizable competitor's trade dress.
- **No generic AI-generated aesthetic.** Prohibit synthetic-looking holograms, meaningless floating 3D glass objects, purple-blue gradient overload, random neon glows, futuristic circuit motifs, overly rounded template cards, unmotivated illustrations, stock-dashboard grids, fake chrome, or repeated gradient hero panels.
- Build **editorial, human-designed layouts** with strong typography, generous but disciplined whitespace, compelling real-project media, deliberate asymmetry where helpful, consistent geometry, restrained motion and excellent information hierarchy.
- Investigate a premium visual palette based on **deep ink/graphite, warm off-white, confident cobalt/royal blue**, and a **small controlled high-energy accent** (possibly lime, signal orange, or vivid coral). Test more than one deliberate palette internally; select the one offering the most distinctive, legible and culturally appropriate product identity. Avoid using every accent at once.
- Deliver complete light and dark themes; color tokens must be semantic and accessible. Color must never be the sole signal for stage, trust, status, or danger. Respect WCAG 2.2 AA contrast and interaction requirements.
- Typography must be engineered: hierarchy, optical alignment, weight, tracking, line length, dynamic type, multilingual support and readable small-screen sizes. Use appropriately licensed typefaces and never redistribute font binaries without authorization.
- Use *authentic project photography, prototype demos, approved institutional content and real artifacts* when eventually available. Until then, use unmistakably labeled **fictional test content** with tasteful placeholders; do not fake a real campus partnership, founder endorsement, investment, science result, or competition winner.
- No unapproved logo should be treated as final. Maintain an easily replaceable brand identity package and design tokens while using **I2V Exchange** as the working product label.

### Navigation and interaction

Design the information architecture deliberately instead of adding a separate tab for every feature. Aim for a highly usable mobile entry point with **Discover, Arena, Network, Workspace, and Exchange** (adapt labels after actual usability reasoning). Cross-cutting elements such as **I2V Next Move, Intelligence, inbox, notifications, search, and profile** should appear where context makes them useful, not become an overwhelming maze.

Include expert global search with intelligent filters, clear back navigation, deep links, saved views, contextual breadcrumbs on web, informative empty states, onboarding paths matched to role, a universal command/search surface where appropriate, and progressive disclosure of complex actions. Use meaningful skeletons, subtle tactile motion and recovery states. Avoid gesture-only controls.

A guest should be able to browse approved public projects without handing over ID documents. Private material requires explicit, purpose-bound authorization. Make the next relevant action obvious on every important page.

### Distinctive interaction concepts

- **Living project stories**: each project is an evolving editorial profile with media, mission, evidence, current needs, milestones, team, events and outcomes.
- **I2V Next Move**: founder-specific, explainable recommendations that take users directly to useful actions rather than simply generate text.
- **Contextual exchange actions**: request a demo, collaborate, mentor, invite to pitch, offer a pilot, discuss licensing, follow progress; user controls access.
- **Real competition energy**: remarkable season pages, structured brackets/rounds where applicable, verified achievements, transparent judging, pitch schedules, team stories and post-event continuation.
- **Meaningful notifications**: relevant opportunity identified, mentor replied, pitch invitation received, milestone approved, deadline approaching—not manipulative alerts.

## 8. QUALITY STANDARD: NOT JUST FUNCTIONAL, EXCEPTIONAL

Each meaningful feature must be evaluated against **six gates**:

1. **Experience:** delightful, legible, intuitive on small mobile and large web, with coherent action placement and distinctive craft.
2. **Functionality:** real workflows, correct transitions, data persistence where intended, validation, permissions, empty/error/offline/loading states and graceful recovery.
3. **Security:** both allowed and denied flows tested, including cross-user, cross-organization and public/private separation.
4. **Accessibility & internationalization:** screen-reader labels, keyboard navigation, focus states, dynamic type, motion settings, contrast, locale/time-zone/currency formats and adaptable layouts.
5. **Performance & reliability:** measured screen startup, interaction latency, image payload, search responsiveness, memory and network behavior; suitable for constrained devices and intermittent connections. Record performance budgets based on actual target-device tests rather than made-up claims.
6. **Maintainability:** typed boundaries, unit/integration/end-to-end tests, code review, migration discipline, observability, clear component ownership and documentation.

Automate formatting, lint, typechecking, test suites, API contract tests, security-sensitive regression cases, accessible web checks, representative mobile interaction checks, dependency scans and CI. Add integration/performance/load tests appropriate to actual functionality. Record which commands ran and which were blocked by environment limitations.

Provide a repeatable screenshot/design review process comparing important flows at multiple screen sizes and themes. Refine awkward spacing, hierarchy and navigation; do not accept first-pass AI-looking templates. Build a reusable component library and state catalogue rather than copying screens.
